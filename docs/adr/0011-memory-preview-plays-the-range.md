# 内存预览（Shift+B）＝ 把这一段**真的播一遍**，而不是自己渲像素存起来

## Status

accepted

## 背景

用户要求复刻 Vegas Pro 的 Shift+B——"动态 RAM 预览"：把一段范围预先渲进内存，
之后播这一段就顺了。直觉上有两条路：自己渲、自己存、播的时候把画面盖回去；
或者想办法让 Blender 自己的 VSE 缓存把这段装上。真机实测（2026-09，
`.scratch/ram-preview/probe_004/006`）把这条路砍成了唯一：

- **Blender 的 VSE 缓存可观测**：`scene.sequence_editor.cache_final_size`
  是真可读的整数（单位约 MB），这是整个功能的仪表。
- **缓存命中让预览快 4.8 倍**：6 层 1080p 合成、同一 8 帧，逐帧重绘延迟
  **缓存关 48.1ms / 缓存命中 10.1ms**。这个功能是有效应的，不是心理作用。
- **标定（`.scratch/ram-preview/probe_008`）**：`cache_final_size` 单位约
  **MB**，一个 1080p 的画面约 **7.9MB**（理论 RGBA8 值 7.91MB，实测
  "整段时间线 24 帧 → 189MB" 与之吻合）。**但它的粒度不是"访问过的帧"**：
  播过去两三帧后整个条带的帧会一次性进缓存（189MB 恒定出现，与
  `use_cache_raw` / `use_prefetch` 的开关无关）。所以它只能当"有没有东西
  进了缓存"与"是不是已经顶到上限"的信号，**不能当帧计数器用**。
- **逐帧 `frame_set` + 重绘不写缓存**：预览确实画了 22 次，
  `cache_final_size` 纹丝不动。**只有"真的播"（走 `animation_play`）才会写。**
- GPUOffScreen 抓不了序列预览窗，所以"自己渲 + POST_PIXEL 盖回去"那条路
  除了 8MB/帧的内存账单，还要额外承担"渲染分辨率不是预览分辨率"的错位。

## 决定

1. **插件一根像素都不碰。** Shift+B 的产物不是我们自己的像素缓冲，而是
   **Blender 自己 VSE 缓存里装有那一段**。播放＝渲染＝导出同一条原生管线
   ——这与本插件一贯的"只操作原生数据"原则（ADR-0002）一致。
2. **构建＝在范围内起一次真播放**：从范围起点播到终点，期间锁交互；播完
   （或中止）一律把播放头送回**范围开头**。这是 Vegas 的行为，也是
   Blender 唯一认的方式——不是巧合。
3. **播放必须 `sync_mode = NONE`**（断音画同步）。卡着 24fps 的节拍走会把
   构建时长锁死成素材时长；而 **`FRAME_DROP` 绝不能用**——被跳过的帧根本
   不会被渲染，也就不会被缓存，功能当场报废。
4. **范围**：勾了预览范围就用预览范围，否则用场景渲染范围；一律经
   `regions.displayed_scene()`（序列场景）取，不经活动场景（ADR-0003）。
5. **失效＝整个作废**：序列场景里**任何**改动都会让已构建内容作废。理由：
   Blender 自己的失效是**部分的**（实测挪条带 channel 45→43MB，改名毫无
   反应），指望它清干净等于留下过期画面；而 Vegas 的语义本来也是这样。
6. **取消≠失效**：Esc 中止保留已构建部分，并如实报告"构建到第 N 帧"。
   清空只有一种代价要认领：`use_cache_final` 拨 False 再拨回来会连带把
   Blender 自己积累的缓存一起清掉（全局副作用，不是精确地只清我们的）。
7. **内存不足＝构建到放不下为止**：按下时按帧数估算一个**预告**（1080p 约
   7.9MB/帧，默认上限 4096MB ⇒ 五百帧上下、二十秒量级），并在播放过程中
   **盯 `cache_final_size`**：体积不再长大且已贴近上限 → 提前收摊，报告
   "已构建到第 N 帧为止"。
   **收摊的主判据永远是播放头走到范围末尾**，水位 watch 只负责"顶到天花板
   就别再渲了"这一种提前中止——因为缓存体积**不按帧线性增长**（见背景），
   它既不能当帧计数器，也不能反过来推断"已经构建完多少"。构建水位取那时
   的**播放头帧**，不取字节数换算。
   **"顶到天花板"怎么判（2026-09 真机标定，见下）**：Blender 不会把
   `memory_cache_limit` 用满，最终水位比上限低**几百 MB 的绝对空隙**
   （上限 4096MB 时实测停在 3860MB 与 3978MB 两处）。所以门槛要同时认
   **比例（≥90%）**与**绝对空隙（离上限 ≤300MB）**两条，取更宽松的那个；
   只按 95% 认的那一版就是漏判（水位 3860MB = 94.2% 够不着），症状是
   **宣称整段构建完成、其实后面的帧根本没留下**。
8. **构建期间临时接管**三项用户设置：`use_cache_final`、`sync_mode`、
   `use_audio`（静音）——一律"存旧值 → 改 → 结束/取消/**异常**时还原"，
   且不得进撤销栈。**`memory_cache_limit` 一根手指都不许碰**（那是全局
   用户偏好，改它就是越界）。

## 真机标定（2026-09，`.scratch/ram-preview/probe_011~014`）

决定 7 的水位判据与"已构建到第 N 帧"这句话的诚实性，都是在这几轮里实测
出来的；当初凭直觉写下的那一版（95% 比例门槛）当场被证伪：

- **天花板上不是 `memory_cache_limit` 本身**。上限 4096MB 时，水位停过
  3860MB（94.2%，单层短条带）与 3978MB（97.1%，8 层长条带）两处。留的是
  **几百 MB 的绝对空隙**，不是固定比例 ⇒ 门槛必须"比例 **或** 绝对空隙"取
  宽松者。只认 95% 的那版在 3860 这一档永远等不到"满"，症状是**宣称整段
  构建完成、其实后面的帧根本没留下**（probe 011 实测：900 帧跑到 900 还报
  `finished`，而缓存只够装约 490 帧）。
- **装不下时保留的是开头，不是最后一段**（probe 013：掐掉早停、硬跑完 900
  帧后，第 1/50/150 帧重绘 3.5~4.5ms（命中），冷测同帧 20~30ms；第 300 帧
  之后才回落到十几毫秒）。也就是说 Blender 到顶后只是**不再收新的**，并不
  把先来的挤出去——这与 Vegas 的"渲到哪里算哪里"一致，所以"保留到第 N 帧"
  的说法成立，**别把它改成"最后 N 帧"**。
- **到顶后继续渲没有意义**：既然不再收新的，接着播只是在空转。早停把一次
  超长范围的构建从 38 秒压到 5.5 秒（probe 014：8 层 900 帧 → 第 119 帧
  收摊，`outcome=full`）。
- **"第 N 帧之后一定还是冷的"不成立**：Blender 自带的 `use_prefetch` 会
  （在我们不动它的情况下）继续往前烘焙，所以 N 是**下界**，报出来的那些帧
  必定是热的，之外可能额外热一点。断言时可以钉"第 N 帧以内是热的"，
  不许钉"第 N 帧以外是冷的"。
- **播放期间键盘事件照旧进得来 modal**（实测观察到的事件类型：`TIMER0`
  （播放自带）/ `TIMER`（我们的轮询）/ `MOUSEMOVE` / `ESC`），因此 Esc 中止
  这条路可用。反过来说也有一条提醒：**注入式按键在本机是 flaky 的**
  （同一段也曾一次没生效），写判定时请用"从外部停掉播放"这类确定性手段，
  别把 flaky 结论当成产品行为。

## 考虑过的选项

- **路线 B：自己 `render.opengl(sequencer=True)` 渲 → 读回像素 → 存在自己
  内存里 → POST_PIXEL 盖在预览窗上**（Stax 的手法）。否——每帧自负
  8.3MB 的内存账单（同类内存里比路线 A 少装好几个数量级），渲染用的是
  **场景渲染分辨率**而非预览分辨率、不吃代理与预览画质，画面会错位；且
  预览窗被隐藏或切成别的区域时整个功能失效。只在路线 A 被证伪时才考虑。
- **静默逐帧推进**（`frame_set` + `tag_redraw`，播放头可以保持不动、
  画面不扫）。否——**实测假阴性**：预览确实画了 22 次但缓存一个字节都没
  进。这条路最诱人（看起来最优雅、最"不像在播放"），也最致命。
- **交给 Blender 原生 `use_prefetch`**（后台往前预烘焙）。否——无法指定
  范围、只从播放头向前，且命中情况无从交付给用户。
- **存磁盘 / 建代理**。否——那就不是"内存预览"了，还会引入文件生命周期
  与失效不及时的麻烦。

## 后人不该"简化"回去的理由

失败模式非常具体：**后来的人看到构建流程居然是"启动一次播放"，会认为这
是粗陋的实现，顺手改成"循环 `frame_set` 逐帧推进"——改完之后代码更干净、
播放头也不乱跳，唯一症状是这一段的播放**一点都没变快**，而 `cache_final_size`
几乎没人会去看。**这个功能是"跑得通但没效果"的那类 bug**，单测全绿、
画面正常、用户只觉得"这插件好像有点用又好像没用"。因此：本功能的测试判据
**必须断言 `cache_final_size` 增长 / 逐帧重绘延迟下降**，不能只断言"播放头
前进了"。同理，`sync_mode` 若被误改成 `FRAME_DROP`，症状也是一样的"全绿
但无效"。

## 测试影响

- **无头（`--background`）无法验证本功能**：headless 从不 Paint，缓存恒 0。
  必须走 GUI 真机；可用"进程内 `AttachThreadInput` + `SetForegroundWindow`"
  抢前台（`.scratch/ram-preview/probe_004.py` 已验证有效；注意 `EnumWindows`
  回调要用 64 位原型，否则 hwnd 恒 0）。
- **判据不可只数"播到第几帧"**：素材解码成为瓶颈时（瓶颈不是合成），开
  关缓存都是同一个 fps，测不出差别。必须测**逐帧重绘延迟**（`frame_set` →
  PREVIEW 区域 POST_PIXEL 回调触发的间隔）。
- **字节级判据的分工（2026-09 落实）**：`cache_final_size > 0` / 改动后归零
  这类断言只能活在 GUI 真机（`.scratch/ram-preview/` 的探针已手工等价验证，
  probe_014：`outcome=full`、水位 119、N 以内确为热）；无头能测的另一半——
  范围/水位判定、出口语义、收摊还原——已固化进 `tests/test_ram.py`（零 bpy
  规则层）与 `tests/test_preview.py`（bpy 胶水，假播放驱动）。**别把这两半
  混成一摊**：在无头里假造"缓存涨了"或拿探针冒充回归套件，都是撒谎。
- 面板新增"内存预览"分区（ADR-0009：静态层字符串常驻英中双语，运行层经
  `i18n` 表），键位加在**编辑器键位表**（工具键位表只挂
  `seqvel.edit_speedline`，本功能不该参与工具模态）。
