# 速度标尺铺满条带绘制区（通道高度的 5%~95%），不是整个通道带

## Status

accepted

## 背景

用户真机报告：极限速度下速度线肉眼可见地"出界"——线的上下边界比素材的上下
边界宽。排查 Blender 源码实锤了根因：

- 条带主体在通道带里**上下各内缩 5%**：`STRIP_OFSBOTTOM = 0.05f`、
  `STRIP_OFSTOP = 0.95f`（`DNA_sequence_types.h`，2.80 起从未变过），即条带
  绘制高度只有通道高度的 **90%**，与通道高矮、选中态、条带类型无关，且
  **没有**"通道太矮就不内缩"的分支。
- 本插件 `speed_to_yfrac` 把 `0 ~ 显示范围上限` 的标尺**铺满整个通道高度**
  （`view_to_region(frame, channel)` 返回的就是全带），于是上限速度的线比
  素材上缘高出 5% 通道高度，底端也低出 5%。

## 决定

1. **标尺 `0 ~ 上限` 铺满条带绘制区**（通道高度的 5%~95%）：上限速度的线
   正好贴素材上缘，`SPEED_MIN` 贴素材下缘，**不留任何安全余量**——"贴到
   上缘 = 到达上限"是最清晰的视觉语义，加余量反而让"到底拉没拉满"变模糊。
2. **变换集中在 `curve.py` 的标尺映射对**（`speed_to_yfrac` /
   `yfrac_to_speed` / `yfrac_to_speed_raw`）：`yfrac` 的语义改为"条带绘制区
   内的比例"，合法区间从 `0..1` 变为 `0.05..0.95`。绘制、命中、拖动、悬停
   全部共用这一对函数，**一处改、处处一致**；禁止在 `geometry.py` 像素层
   另打补丁。
3. **不避条带头部文字区**：Blender 会在条带顶部画名字标签（内容区顶部最多
   再下移 20 像素），速度线是叠加层，压过名字标签是 Vegas 速度线的正常
   形态；避开会白白损失一大截纵向空间。
4. **数据不动**：曲线存的是绝对速度值，本次是纯视觉重标定——已有曲线的
   画法整体轻微"压扁"10% 属预期，不需要任何迁移。

## 考虑过的选项

- **在 `geometry.py` 像素层做内缩变换**（`point_xy` 与鼠标反算处各补一刀）：
  否——映射契约在 `curve.py`，未来任何直接调用映射对的代码会悄悄不一致。
- **避开条带头部文字区**：否——代价是纵向空间损失最多 20 像素（通道越矮
  相对损失越大），换不来说不清的收益。
- **上限留 1~2 像素余量**：否——见决定 1。
- **维持现状（铺满通道带）**：否——可见边界之外画线，违背"可见＝可抓"
  的原则（ADR-0005）。

## 后人不该"简化"回去的理由

失败模式很具体：**后来的人看到标尺区间是 `0.05..0.95`，会以为是魔法数或
笔误，顺手"改正"成 `0..1`**——改回去后绘制、命中、钳制仍然自洽、不会报
错，唯一的症状是极限速度的线重新溢出素材边界，而这个问题当年是被真机
复核过的。`0.05 / 0.95` 不是插件发明的数，是 Blender 条带绘制的常量
（`STRIP_OFSBOTTOM / STRIP_OFSTOP`），任何调整都必须以 Blender 源码为准。

## 测试影响

- `test_curve` 里"1.0x 落在垂直 1/3 处"（cap=3）：新期望为
  `0.05 + 0.9/3 = 0.35`。
- ADR-0005 修订 R11 的去饱和像素外插用例（越界光标像素从档顶外插）需按
  新映射重做：标尺顶端从通道顶移到了素材上缘。
- e2e 存量红 `t4/t5` 的像素坐标会随映射变化整体平移——它们本来就红
  （needs-triage），本次不处理。

# 修订 R1（v1.6.6）：底部再留 4% 通道高，顶端仍贴边

## 背景

真机上看曲线：最低速那条线糊在素材下缘上，整条线显得"太满"。用户要求
**在 R0 的 5% 之上再把下界抬一点**，让整条曲线看着更扁，并明确两点：

- **顶端不动**——那个位置在前一版已经调合适了；
- **不按像素算**——"省的缩放轨道时有 bug"。

## 决定

1. `SCALE_BOTTOM` 从 `0.05` 改为 **`0.09`**（= Blender 的 `STRIP_OFSBOTTOM`
   0.05 **＋ 插件自己的 4% 底部留白**），`SCALE_TOP` 保持 `0.95`，跨度
   `0.90 → 0.86`。标尺合法区间从 `0.05..0.95` 变为 **`0.09..0.95`**。
2. **顶端不留余量**（R0 决定 1）不变："贴到上缘 = 到达上限"。
3. **用通道比例，不用像素。** VSE 里一个通道的屏幕像素高随编辑器高度变化
   （实测 region 高 755px → 88.5px/通道，438px → 51.25px/通道，恒可见约
   8.5 个通道）。像素余量会让"压扁的程度"随窗口高矮漂移；比例余量让观感
   与窗口大小无关。4% 通道高在 88.5px 的通道上约 3.5px。
4. **数据不动**（同 R0 决定 4）：纯视觉重标定，老曲线只是整体被压扁。

## 代价（明确接受的）

- 最下面 4% 通道高是**死区**：光标拖到条带最底仍被钳成 `SPEED_MIN`，但线
  画在留白之上——"光标到底 ≠ 线到底"。
- 曲线不是平移而是**压扁**，越靠下抬得越多：最低点抬 4%（通道高），中点抬
  2%，`1.0x`（cap=3.0 时位于标尺 1/3 处）抬约 2.7%，顶端 0。
- 底部那个 7px 方块（半宽 3.5px）只在**高通道**上刚好贴住素材下缘：
  88.5px 的通道留白 3.54px ⇒ 方块下沿差 0.04px；而编辑器压矮到 51.25px
  通道时留白只有 2.05px，方块照样探出约 1.45px。想让它**永远**缩进去，
  得按方块尺寸定留白（≈7px 起），不是改比例——这正是"按比例留白"的代价。

## 后人不该改回去的理由

`0.05` 是 **Blender 的常量**，`0.09` 是"Blender 常量 **＋** 4% 刻意的视觉
留白"——两者来源不同，别揉成一个数、也别在注释里写成"Blender 内缩 9%"。
同样**别"对称地"给顶端也加 4%**：那会重新引入"上限线不贴边"的问题，R0
决定 1 的"贴到上缘 = 到达上限"就没意义了。

## 测试影响（R1）

- 钉 `0.05 / 0.9` 的断言改为 `0.09 / 0.86`：`test_curve`（1.0x 落点、
  `SPEED_MIN` 落点）、`test_speed_cap`（档内 1/10 落点、未钳映射）、
  `test_geometry`（像素 y）、`test_session`（换算率 `3.0/(0.86×60)`）。
- 断言里**继续写死数字**（不改成引用常量）：R0 的"防后人简化回 0..1"
  靠的就是改常量必须撞红。新增一条"底部留白恰为 4% 通道高"的语义用例
  （判据走 `yfrac_to_speed_raw`：`speed_to_yfrac(0.0)` 测到的是"0 被钳到
  `SPEED_MIN`"，与留白无关）。
- 两处**布景**随之重调（映射变了，几何跟着变）：
  `test_session` 的深 V 拐点 0.5 → 0.2（跨度 0.86 后 12.1px 处离段0 已是
  8.15 > 段半径 8，用例会退化成"只有一段在半径内"）；`test_geometry` 的
  平手像素 13.0 → 13.5（"逐位等距"是浮点上的恰好，13.0 在新标尺下差 3e-15）。
- 三条用例改名：`..._of_the_strip_extent` → `..._of_the_ruler`（1.0x 落在
  **标尺** 1/3 处；绘制区的 1/3 是 0.35，不是现在的 0.377）。
