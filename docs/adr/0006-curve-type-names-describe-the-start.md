# 段曲线类型档名描述"变化集中在哪一端"，不是凸向

## Status

accepted

## 背景

四档档名（线性 / 平滑 / 快速 / 慢速）复刻自 Vegas Pro，但"快速""慢速"到底
描述什么，历来只写在公式里、没写进任何文档：

- `FAST = 1 − (1−t)²`（起步急促、收尾平缓）
- `SLOW = t²`（起步平缓、收尾急促）

于是唯一能判断档名对不对的依据是"看公式猜语义"。2026-09-15 用户真机复核时报
"快速 / 慢速大概率标反了"（理由：从速度线和对应效果看）。实测后确认
**没有标反**，误判的根因是凸向：

| 段 | 「快速」 | 「慢速」 |
|---|---|---|
| 上升（100% → 300%） | 中点 2.500x，弦 2.000x → **上凸** | 中点 1.500x → **下凸** |
| 下降（300% → 100%） | 中点 1.500x → **下凸** | 中点 2.500x → **上凸** |

同一个「快速」，升段上凸、降段下凸。拿"凸向"当判据，恰好会得出"升段对、
降段反"的结论——而档名从来没有随方向翻转。

（Vegas 的公开资料查不出定论：Sony/MAGIX 原文只有"快/慢对数路径"一句、无形状
图，中文 wiki 与英文帮助互相矛盾。最终以用户真机复核为准：同样选「快速」，
小变大上凸、大变小下凸，斜率都是先大后小。）

## 决定

1. **档名描述"速度变化集中在段内的哪一端"，与段是升是降无关。**
   「快速」= 起步那半段就把大部分变化吃掉（先陡后缓）；「慢速」= 起步平缓、
   后段才急促地变（先缓后陡）。
2. **判据用归一化进度，不用凸向**：`(v(t) − v0) / (v1 − v0)` 在 `0 < t < 1` 上
   恒大于 `t` 即「快速」，恒小于 `t` 即「慢速」。该判据对升段、降段同时成立。
3. **凸向不是判据**：线的凹凸随升降方向自然翻转，是同一个形状的两种朝向。
   不许因为"降段看着跟升段相反"而交换档名或交换公式。
4. **现状的公式与档名即为正确实现**（`FAST = 1 − (1−t)²`、`SLOW = t²`），
   **不改行为**。本次只补文档与带语义的回归用例。
5. 「线性」「平滑」不受影响：线性无从反；平滑 = `3t² − 2t³`（两端平缓、变化
   集中在中间、两端切线水平），同样与方向无关。

## 考虑过的选项

- **对调两个档名**（用户最初的要求）：否——实测现状与 Vegas 一致，对调会把
  升段弄反。误判来自凸向，不是来自命名。
- **改公式：把「快速」做成 `t²`**：否——那会让上升段的「快速」变成先平后陡，
  与"起步急促"的命名语义相反，且与真机复核结果矛盾。
- **菜单文字加括注**（如「快速（起步急促）」）：否——菜单保持 Vegas 同构的
  四个纯名（用户明确要），形状说明放 `README.md` 与 `CONTEXT.md`。

## 后人不该"简化"回去的理由

失败模式很具体：**后来的人看到 `FAST` 用的是 `1 − (1−t)²` 而不是显眼的 `t²`，
会以为是笔误**；或者看到降段的线朝向跟升段相反，以为档名标反，于是"顺手
改正"——一次性把两个档名都弄反，而线上形状仍然"看着合理"，不会报错。

回归用例必须**带语义**地钉住判据（`test_fast_is_ahead_of_the_chord_and_slow_is_behind`、
`test_bulge_flips_with_direction_but_the_name_does_not`、
`test_each_menu_label_maps_to_its_declared_shape`），不要只钉数值：
纯数值断言拦不住"翻回去"，带语义的用例名才拦得住。
