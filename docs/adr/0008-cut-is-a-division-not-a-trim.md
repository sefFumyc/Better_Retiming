# 切断是划分，不是裁剪

## Status

accepted（2026-09-16 全部定案：决定 1–4 是**语义**，决定 5–6 是**修补什么时候落盘**。
"只在内存里、永不写回文件"就是决定 6 —— 它不是留待实现决定的细节）

## 背景

素材上已经有速度曲线时，把它在某一帧**切断**（Blender 的 Split / `K`）会同时出两个错：

1. 前半段的曲线**保留切前的长度**（末点仍在条带右端之外），拖一下任意一半才自愈；
2. 后半段**完全继承了前半段的开头**——像曲线被整份复制了一份，而不是在切点处另起一点、承接原曲线在该帧的值。

根因不是"忘了更新"，而是**模型从没被当作"被切开"过**。实测（Blender 5.2.1，`.scratch/probe_split/`、`.scratch/probe_carrier/`）：

- 原生 `split()` 把自定义属性（`seqvel_curve` / `seqvel_curve_types`）**逐字复制到两半**；
- 左半是**原对象本身**（名字不变），右半是**新建对象**（`.001`）——所以左半命中的是"同一个条带标识"，右半拿到的是"一份原点在别人身上的坐标"；
- 承载侧（`SPD_`）被一起裂成两条，各有一份 `speed_factor` fcurve，key 都是原区间的逐字复制、**没有重锚定**；而 VSE 条带的关键帧是按**时间轴绝对帧**求值（实测）——因此承载侧在切断后**恰好已经是"忠实切片"**，错位的只有模型/属性这条通道；
- `split()` **不上报 `depsgraph.updates`**，所以挂在依赖图上的端点监听器可能一次都不跑（症状 1 的"拖一下才自愈"即由此而来）。

## 决定

1. **切断 = 纯划分**：曲线被同一根切点竖线切成两半，左半留下切点之前的部分、右半留下切点之后的部分。**两半的并集与切之前逐帧相同**——切断不改变素材内容，也不在接缝处凭空造出速度台阶（判据：**接缝两侧速度必须相等**）。
2. **切点落在某一段内部时**，两半各自在切点处得到一个端点：左半的末点 / 右半的首点，**速度取原曲线在该帧的插值**（即"插一个点、线不动"的既有语义）；切点正好落在已有点上则不插新点，两半共享该点。曲线末点本就在切点之前时，两种取值方式数学等价。
   - **被劈开的那一段若带缓动（平滑 / 快速 / 慢速），两半各自把它逐帧展开成线性小段**。理由不是审美：一截缓动的形状**不在四档里**（"S 形的前六个百分点"既不是 S、也不是任何一档），若让该档把缩短后的区间重新铺满，形状当场就变；而承载侧是按**绝对帧**逐帧写 key 的（`Curve.keyframe_frames`），于是"画出来的线"与"实际播出来的速度"分家。逐帧展开正是承载侧在做的事，两边的每一帧因此严格相等。**整段落在切区里**的段不受影响（同样的两端点 + 同样的区间长度 ⇒ 同一档缓动，逐帧完全相等），只有被切点劈开的那一段会变密。实测数：`1.0x→3.0x` 的平滑段铺在 0..60，第 1 帧原本是 `0.501648…`，"重新铺满 0..10"会变成 `0.504148…`。
3. **切点归右半**：左半的区间是切点之前、右半自切点开始（原生即如此，实测左 `1..50` / 右 `50..101`）。因此切断后**左半的相对帧原点不变、右半的原点就是切点**。
4. **切断不走「末端跟随」**：`carry_tail`（压缩末段 + 吞点）是**裁剪**（拖右端句柄、缩短素材范围）的规则，不是划分的规则。切断既不"带"点也不"吞"点。
5. **载荷自描述"它是在哪段区间上写的"**：写入侧（`commit`）在写点与段类型的同时，记下这份载荷所属的**绝对区间**；读不到这条记录（旧 .blend）一律按"**区间未知**"处理——走今天的语义（读取时静默钳回 / 末端跟随），不猜测、不迁移。它与点、类型**同进同退**，理由同 ADR-0007：多一条自描述字段，比让读路径去猜"这份坐标的原点在哪"便宜得多。
6. **修补只发生在内存里，不写回文件**：读路径发现"载荷声明的区间 ≠ 本条带区间"时，当场在内存里把它切成它该有的样子；**属性与关键帧一律不动**。文件里的旧数字要等到下一次真正编辑这条曲线时才顺带写干净。

**代价与前提（明写）**：切断后立刻存盘退出，文件里留的是旧数字。这条只有在**修补是确定性重推导**时才可接受——同一个文件重开一次，读路径必须算出同一个结果。因此判据必须是**落盘的证据**（载荷声明的区间 + 相邻条带的区间拼接），**不许**依赖"本次会话记住的"内存状态，**不许**用定时器去补。证据式判据也正是"不写回"能成立的全部原因：写回发生在切断**之后**，天然会多出一个撤销步（Ctrl+Z 先撤销一个看不见的修补，看着像没反应），而不写回一个都不会有。

## 考虑过的选项

- **左半沿用末端跟随（压缩式）**：否。它是"裁剪"的语义，用在这里会有三处硬伤：① 接缝处出现速度台阶（例：`1.0x→3.0x` 的线性段切在中点，左半压缩成 `1.0x→3.0x` 落在半个区间上、右半首点却是 `2.0x`，接缝处 3.0 直落 2.0）；② 左半在同样的时间轴长度里吃掉**更多素材**，与承载侧按原曲线算出的源区间打架，等于**切断改变了素材内容**；③ 会顺手"吞"掉切点右侧的点，而用户要的是"切点之后的点跟着右半走"。
- **右半沿用原生复制的那份（现状）**：否——那是"前半段的开头"，不是"这个位置的曲线"；用户报告的第二个症状就是它。
- **只改模型、不动承载**：可接受（承载实测已近似切片），但**不能依赖**"恰好对"；模型一旦被编辑就会全量重写承载，因此承载随之收敛。

## 后人不该"简化"回去的理由

"模型不随条带变化"是 ADR-0004 写下的语义（`set_duration` 只改钳制范围），那条语义对**左端裁剪与整体移动**成立，对**右端收短**由监听器接管，而**切断**是第三种情形——它既不是"条带变短"，也不是"不变化"，而是"**同一份曲线的坐标原点被劈成了两个**"。

最容易被"简化"掉的正是决定 4：看到切点处也是"右端变短了"，就把切断直接扔给 `carry_tail` 处理——那会静默地把曲线的形状压扁、并吞掉切点右侧的点。回归测试须覆盖：**接缝两侧速度相等**、**两半并集 = 切前逐帧**、**切点落在段内部 / 落在已有点上 / 落在末段之外**三种位置，以及**左半的曲线不因切断而被压缩**。

决定 6 的判据同样有两个诱人的错法：**① 拿"载荷溢出自身时长"当唯一判据**——拖右端句柄时载荷同样会暂时越出条带，于是裁剪被误判成划分，末端跟随的手感当场被改掉；**② 干脆"读取时一律切片"**——同一个下场，而且事后无法分辨。切断的**专属证据**是"相邻两条贴合条带的区间能**恰好拼回**载荷声明的区间"（`CONTEXT.md`「划分链」，详见 `.scratch/strip-cut/spec.md`）：**只有划分会把一条载荷复制成拼得回去的两半**，复制粘贴、裁剪、改名都不满足。

决定 2 的逐帧展开看着"让模型的点变多了"，很可能被当成浪费而砍掉。它不是：缓动段被劈开后，**四档里没有任何一档能表示被切出来的那一截**，省掉逐帧展开就等于静默改形状——而承载侧的 key 是按绝对帧写的，改掉的正是"用户实际会看到的速度"。测试钉住了这一点（`test_curve.TestSliceBetween::test_half_of_an_eased_segment_is_never_reshaped`，同时给出"正确值"与"铺满后的错误值"）。

## 修订 R1：切断之后不许任何人在模型上"写回"（2026-10-17，v1.6.5）

**症状（真机复发）**：素材上已经有速度线，按 `K` 切断 → 右半**莫名其妙变成前半段的复制**；而且**一次 `Ctrl+Z` 就能修好、却不撤回切断，按两次才撤回**。

**根因**：决定 6 只把"不许写回"写给了**读路径**，漏了**监听器**。切断本身不上报依赖图更新，但 GUI 里切完必然有一次重绘/求值，`watch` 于是看到"左半的区间变了"，把**左半的切片连同新区间 `[1,51]`** 写进属性（`STORE.commit` 默认 `write_prop=True`）。这一写正是决定 6 明文禁止的事：

- **证据被擦掉**：两半载荷不再逐字相同 → 划分链当场不成立 → 兄弟退回"整份载荷按自己长度钳回"，右半于是画出前半段的形状；
- **多出一个隐形撤销步**：`Ctrl+Z` 先撤销这次写回（线看着"好了"），第二次才轮到切断。决定 6 当初预言的"看着像没反应"，在用户这里长成了"按一下就好、按两下才撤"。

实测（`.scratch/cut-regress/evidence.md`，原始读数在同目录 `report_cut_watch.json`）：切断当刻两半都正确（左 `[(0,1.0),(50,2.0)]` / 右 `[(0,2.0),(50,3.0)]`、链成立）；**一次** `observe_scene` 之后左半载荷变成 `[0,1.0,50,2.0]` + 区间 `[1,51]`、链变空、右半读成 `[(0,1.0),(50,3.0)]`。

顺带查出同根的第二症状（同目录 `report_half_edit.json`）：切断后**编辑任意一半**（拖个点，一次真实编辑），另一半会被拉成压缩形状——左半末点从接缝的 `2.0` 直接跳到 `3.0`，凭空一个速度台阶。原因同上：那一半的载荷被改写，链就断了。

**决定**：

1. **监听器对"划分成员"只落地、不写载荷**。判据用 `STORE.is_division_member(strip)`（＝ `division_chain` 成立，只吃盘上证据，不新增内存状态）。切断之后**模型载荷零写入**（承载层的对齐与映射表重建照旧——那是派生状态，`watch.py` 顶部"别读成'一个属性都不写'"说的就是它）：切断仍是一步撤销，证据也不再被谁擦掉。撤销步数**不能**自动量（本仓库量不到，见技能 §6c），判据是手验：按 `K` 后**一次** `Ctrl+Z` 应当直接撤回切断。
2. **真实编辑时整组物化**：`STORE.commit` 在写本条带之前，把同链其它成员各按自己的区间写成**自描述切片**（自己的点 + 自己的区间）。写完之后每半都自带区间，不再依赖划分链——这是"编辑一半不牵连另一半"能成立的全部原因。
3. **物化必须先算齐、再统一写**：写掉一个成员链就断了，之后再去算别人的切片，拿到的是"整份载荷按它自己的长度钳回"的错形状。这条顺序契约由 `test_cut.CutAfterlifeTest::test_a_three_way_cut_materializes_every_other_member` 钉住（两成员场景区分不出顺序，必须三段）；注入验证 `.scratch/cut-regress/inject.py` 的 `write-as-you-go` 一档把它改成"算一个写一个"，**恰好只有这条转红**。
4. **决定 6 不变**：读路径仍然一个字都不写。这条修订只是把"谁也不许在切断之后写回"从读路径**扩到监听器**，并把"顺带写干净"的时机规定为**一次真实编辑**（落在它自己的撤销步里，不额外多一步）。

**后人不该"简化"回去的理由**：`_commit` 的 `write_prop` 默认值是给"普通裁剪"用的，不是给划分成员用的——监听器里那句 `write_prop = not STORE.reads_as_slice(strip)` 看着像可以省掉的防御，省掉就回到"按 K 就坏 + 隐形撤销步"。同理，别把 `materialize_division` 挪进 `STORE.get`：那等于让读路径写盘，正是决定 6 拦下的事。回归用例：`test_cut.CutAfterlifeTest::test_observer_never_writes_a_division_members_payload`（注入：去掉那句判断 → 转红）、`::test_editing_one_half_leaves_the_other_alone` 与 `::test_edited_group_is_self_describing`（注入：删掉物化调用 → 各转红）。

**已知边界（本次不修，票 04）**：切断之后再**裁剪/移动其中一半**，盘上的区间不再首尾拼回声明区间 → 链断 → 两半都退回老语义（按条带长度收拢）。要救它需要在内存里记住"母载荷"、并处理重开文件后的重推，属于另一个量级；契约是"断了就断，不猜"。
