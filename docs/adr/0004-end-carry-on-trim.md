# 素材收短时末点跟随条带末端（末端跟随 + 吞点）

## Status

accepted

## 背景

影子模型的 `set_duration` 历来只更新钳制范围、不改动已有点，而条带端点变化
（右端被拖短）没有任何监听机制——于是末点的相对帧停在旧位置，被画到条带
右端之外：既是"曲线最末端有个点跃出边界"的视觉 bug，也是"素材收短后末点
悬空"的交互 bug。两个症状一个根因。Vegas 的行为是：事件右端收短越过最后
一个变速点时，该点被带着走。

## 决定

1. **越过才带**：仅当右端收短会越过末点时，末点贴住条带末端跟随；向右拉长
   时末点原地不动，尾段水平延长线变长（保住"拖末点左移 + 延长线补平"的
   现有交互）。
2. **吞点删跟随者，不删挡路者**：末点跟随中将撞上倒数第二点时，删除跟随中
   的末点本身，由倒数第二点升格为新末点继续跟随。若删挡路者，倒数第三点到
   被删点之间的段会突然改道——前面拉好的曲线跳变；删跟随者则在删除瞬间新
   末点恰好位于末端，曲线连续。被吞的点不恢复。保底 2 点（首点 + 末点）时
   末点无条件跟随。
3. **实时跟随**：拖动裁剪的过程中即生效（监听条带端点变化并当场调整模型、
   重写 Speed Control 关键帧与曲线属性），不留"点悬在外面"的中间态。
4. **撤销合步**：跟随不是用户发起的独立编辑，产生的模型改动与裁剪本身合并
   为一步撤销。
5. **历史脏数据静默钳回**：对存量"末点在条带外"的旧数据，读取时把末点钳到
   条带末端。跟随上线后"末点 ≤ 条带末端"成为不变量，兜底只为让旧文件向
   该不变量收敛，没有理由保留一个刚被定义为 bug 的状态。

左端（left handle）的裁剪/移动**不在本决定范围内**：现有左端逻辑（相对帧
原点随左端移动、曲线整体平移）经用户确认符合预期，保持不动。**修订 R1 起**
这条语义要落到承载层上——左端一动，关键帧（按左端写的绝对帧）必须重锚，
否则曲线只是"看起来平移了"，真正播出来的还是旧位置。

## 考虑过的选项

- **末点永久钉死条带末端**：否——会废掉"末点左移 + 尾段延长线"交互，且
  与 Vegas 行为不符。
- **吞点删挡路的倒数第二点**：否——曲线前段会突然改道跳变（用户明确否决）。
- **松手才对齐**：否——拖动中点悬在条带外的中间态正是要修的观感问题。

## 修订（拉长 / 左裁后承载重落地，2026-10-01，v1.6.1；复查收尾 v1.6.2；全量写入收尾重建映射表 v1.6.3；监听目标必须是原始数据块 v1.6.4）

- **R1（修订决定 1、3，并把"只看右端句柄"扩成"看目标区间"）**
  **"拉长不带动模型"不等于"拉长什么都不做"。** 用户报告：有速度线时把素材
  拉长，**拉长出来的那一段不跟着变**——在那一段上做任何编辑它都几乎不响应，
  或者过很久被某个说不清的随机事件"突然修正过来"，且那一段**播放也不正常**。
  - **根因**（上游源码 + 真机探针见 `.scratch/carrier-relaunch/evidence.md`）：Speed
    Control 的源帧映射表 ``SpeedControlVars.frameMap`` 是**惰性构建、建一次
    就不再更新**的——``strip_effect_speed_frame_map_ensure`` 只在
    ``frameMap == nullptr`` 时才建，长度写死为**构建那一刻**的
    ``right_handle − left_handle``；求值时 ``target_frame = s->frameMap[
    frame_index]`` **没有边界检查**。而唯一的重建入口
    ``relations_invalidate_cache()`` 只对"**自己就是 SPEED 条带**"的条带生效，
    目标条带被拉长时 Blender 只把承载条带的 ``enddisp`` 跟着改了
    （``strip_time_effect_range_set``）——**没有任何代码连带失效那张表**。
    于是新长出来的那一段落在旧表之外，越界读到未初始化内存。实测：采样到的
    源帧被钳成**开头那一帧**（画面冻在开头），或乱跳。
  - **旧实现的错**：``watch`` 只观测**右端句柄**，且 ``right >= last`` 直接
    ``return False``——"拉长时末点原地不动"被实现成了"拉长时什么都不做"。
  - **修正**：观测键升级为**目标区间** ``(左端句柄, 右端句柄)``；区间一变就
    重新落地（模型照旧一点不动），按"关键帧要不要重锚"分两条路：
    - **只动右端** → 轻量路径：对齐承载 + **显式强制重建映射表**
      （``carrier.invalidate_speed_map``：重写 ``speed_control``，其 RNA 更新
      回调 ``rna_Strip_invalidate_raw_update`` → ``relations_invalidate_cache``
      → ``strip_effect_speed_rebuild_map``；**同值写也会触发**）。它**返回
      失败原因而不是布尔**（成功是空串），异常原文要一路递到面板——"不静默"
      这条纪律不能断在这一层。**不重写关键帧**——末点没动、尾段是常量外推，
      key 的值与绝对位置一个没变，只缺一张按新长度重算的表。拖右端的每一
      tick 都全量重写会卡（长缓动曲线要写几百个 key）；
    - **左端动了（左裁剪 / 整体移动）或吞了点** → 全量重写：关键帧是按
      ``left_handle + 相对帧`` 写的**绝对帧**，左端一动整条曲线必须重锚，
      否则"画出来的线"与"真正播的速度"当场错开（探针实测：左端 1→31 而
      key 仍在帧 1/51/101）。**曲线锚在条带左端（相对坐标）这条语义不变**
      ——左裁 / 整体移动时曲线跟着**整体平移**；
    - **首次见到**（打开文件 / 撤销 / 重做后跟踪表被清空）补一次**只重建
      映射表 + 对齐**的落地，**不写模型载荷属性**（``seqvel_curve`` /
      ``seqvel_curve_types`` / ``seqvel_curve_range``）：例行自愈不该去动用户
      的曲线数据；载荷区间只在**真的观测到区间变化**时刷新，这也守住了
      ADR-0008"旧文件区间未知时不猜、不迁移"。**这不是"一个属性都不写"**——
      对齐与显示同步照旧做同值重写（承载的 ``channel`` / ``speed_control``、
      目标的 ``show_retiming_keys``），那是派生状态的幂等恢复，不是模型数据。
      至于那些写会不会翻起 Blender 的"未保存"标记：``bpy.data.is_dirty``
      **连"真的改了 ``channel``"都读不出变化**（``--background`` 与真窗口两次
      探针都是 False，校准项当场失效），这个量在脚本层不可观测，所以本文
      不写结论（``.scratch/carrier-relaunch/probe_06_dirty.py`` / ``probe_07_dirty_gui.py``）。
  - **载荷区间跟着走**（本 ADR 决定 5 / ADR-0008 决定 5）：区间一变就
    ``STORE.commit``。不跟的后果是实打实的——拉长过的条带之后再**切断**，
    两半拼不回旧声明区间，"纯划分链"就认不出来，接缝会按普通曲线整条读。
  - **收短路径一并接上**：收短也走同一条落地（吞了点就全量重写），不留
    "有时对有时不对"的第二条路径——否则这个症状会换个形式复发。
  - **真机判据**（``.scratch/carrier-relaunch/evidence.md``；可观测量的构造：源场景的
    世界背景色 = 帧号，于是渲染一帧读回红色就能反推承载实际采样到的源帧）：
    按 100 长建好、渲染一帧让映射表**按 100 落定** → 拉长到 200 → 在 150 帧
    渲染，采样到的源帧**仍是开头**（红 0.0431 vs 对照 0.8549）；先重建映射表
    再渲染，与"从零按 200 建好"的对照**逐值相同**。候选手段里 ``channel`` /
    ``use_frame_interpolate`` / ``speed_control`` 三者的同值重写都有效（选了
    ``speed_control``）；``left_handle`` / ``right_handle`` 对效果条带
    **只读**（``AttributeError``，实测），``sequencer.refresh_all()`` 在无
    界面上下文里 ``poll()`` 失败（"context is incorrect"）。
  - **测试影响**：headless 单测证明不了"缓存里真的换了帧"——那需要渲染与像素
    判读，留在探针层，分工同 ADR-0011。单测钉的是**接线**：区间变化必然触发
    重落地、左端变动必然重锚、只动右端**不写关键帧**、首次见到**不写载荷

    映射表重建**被调用过**、**诊断字段给全**（面板那行"上次写入"不能因为走了
    轻量路径就退化成 ``?``）。
    **纯层与 Blender 层各一套**：纯层六条钉判定矩阵
    （``test_right_extended_relaunches_carrier_without_rewriting_keys`` /
    ``test_left_trim_reanchors_keys`` / ``test_whole_strip_move_reanchors_keys`` /
    ``test_shorten_without_crossing_a_point_still_relaunches`` /
    ``test_first_sight_records_span_and_heals_without_writing_props`` / …），

- **R2（把 R1 的原则推广：重建映射表不是"区间变化"的专属动作，凡改了承载
  关键帧的路径，收尾都必须重建）**
  R1 只堵住了**区间变化**那条路（`relay_span`）。用户复诊："1.6.2 完全没修好——
  拖 `Scene.003` 的末点，对末点右侧那条延长线覆盖的画面没影响，而且**松手后也没
  影响**；拉长后末尾的播放也不正常。" 真机量下来，根因是**全量写入那条路没堵**。
  - **根因**：`carrier.write_curve` 是"`clear_keys` → `insert_keys` 逐个写 key"。
    那张表**除显式重建之外没有任何东西会刷新它**（R1 已量清），写入序列**中途**
    会被建一次，此后所有 key 写入都不再触发重建 ⇒ 整条条带都停在那个中间态。
  - **真机判据**（工程副本逐帧渲染指纹，噪声地板 0，`.scratch/tail-bug/findings.md`）：

    | 状态 | 做了什么 | 与"表是新的"相比 |
    |---|---|---|
    | FRESH | 显式重建，扫 350–442 逐帧 | 基准 |
    | STALE | 再走一遍 `write_curve`，**曲线数据一个字不改** | **93 帧里 89 帧不同** |
    | RESTOR | STALE 之后再重建一次 | **93/93 复原** |

    数据没改 ⇒ "旧表"与"新表"本应一致；不一致就只能是中途建的。旁证：同一份
    错态在两次独立探针里 411 帧指纹**完全相同**（`e1d14b25bcde`），且与"末键被
    改成 0.05 还是 0.3246"**无关** ⇒ 这张表**根本没吃到最后一个关键帧**。
  - **错态不是"空表"**：把 `speed_factor` 关键帧全删掉再渲染，6 帧指纹**全部相同**
    （空 fcurve 积分恒 0 ⇒ 源帧钉在 0 ⇒ 整段冻住），与 STALE 的"6 帧两两不同"不符。
    具体卡在写入序列哪一步**未钉死**，但修法不依赖它。
  - **影响面比"尾巴"大得多**：坏的是**整条**（89/93），不是末点右侧那一段。所以
    用户说的"拖末点什么都没发生"其实是"离末点 49 帧远的地方画面早就错了"，看起来
    才像"末点跟线断了"；而"**松手后也没影响**"正是陈旧表的签名——写 key 不触发
    重建，只有某个不相关动作才会让它"突然自己好了"（这正是用户 v1.6.0 时的原话）。
  - **修正**：`_new_diag` 补 `invalidated`（两条落地路径从此恒带这个键，预置 `False`
    才能把"这一步漏了"与"这一步失败了"分开）；`write_curve` 在**所有写之后**
    （`set_linear_interpolation` 之后）调 `invalidate_speed_map(strip)`，
    `diag["invalidated"] = not reason`，失败原因进 `errors`——与 `relay_span`
    **逐字同形**、同一条 i18n 通路，不新造第二套。放最后一步是因为表必须按
    **最终 fcurve** 重算。
  - **明确不是上游钳制（上一轮的错误假设，当场撤回）**：`Scene.003` 是 SCENE 条带，
    引用场景 `Scene` 的 `[1, 5000]` @ 50fps，外层场景 24fps ⇒ 条带 93 外层帧只摊开
    引用场景的 ≈**194** 帧，**素材远远没用完**。该曲线积分到末尾只有 **104.077**，
    离钳制上限一大截，FRESH 态 350–442 **一条冻结段都没有**。
    `target_frame += speed; CLAMP(...)` 的粘性饱和是真的（压力测试把末点设成 3.0 ⇒
    冻结段 `[[411,412,2],[432,441,10]]`），但它**不是**用户这次的 bug，别拿它解释。
  - **用户的澄清进了判据**：`场景` 的 `use_cache_raw = False` ⇒ SCENE 条带走**子帧
    采样** ⇒ 变速本来就该是"无极"的。于是"尾巴每 3 帧才换一格是慢动作的正常表现"
    这种解释**不成立**；FRESH 态实测 350–442 **没有任何一对连续帧相同**，正是无极。
    这条同时是验收判据：修完必须既"无极"、又与重建过的状态逐位一致。
  - **测试影响**：headless 单测证明不了"缓存里真的换了帧"，像素判读留在探针层

    契约**：收尾必然调用一次重建、且**排在写完 key 之后**、重建对象是**目标条带**、
    `diag["invalidated"] is True`、失败原因**整条走 `carrier.invalidate_failed`
    这条 i18n 通路**进 `errors`、以及**两条落地路径的诊断字段给全**（键集从
    `_new_diag` 现取，不手抄——手抄的清单曾漏掉 `retiming_reset`）。**两种注入各钉一半**：
    (甲) 删掉收尾那三行 ⇒ **恰好 2 条转红**（`test_write_rebuilds_speed_map_after_writing_keys`
    报"少了一次重建"、`test_write_reports_invalidate_failure` 红在 `len(errors) != 1`），
    (乙) 把收尾块**挪到 `set_linear_interpolation` 之前** ⇒ **恰好 1 条转红**
    （`test_write_rebuilds_speed_map_after_writing_keys` 报
    `['keys', 'invalidate:target', 'linear'] != ['keys', 'linear', 'invalidate:target']`），
    两次还原即绿。注意 (甲) 里第二条**不是** `KeyError`：`_new_diag` 预置了 `invalidated`，
    这个键恒在，红的是"`errors` 里没东西"——**这正是预置 `False` 想要的区分度**
    （"这一步漏了"与"这一步失败了"给不同的红）。
    **字段齐备那条两种注入都不转红，是有意的**：它钉"两条路给同一个形状"
    （`_new_diag` 预置了 `invalidated`），"行为漏了"由前一条抓、"形状漏了"由它抓。
    真鼠标 e2e **本条不跑**：它管的是交互 / 键位 / 命中，而本修订只动"写完 key 之后
    多调一次重建"，press-drag-release 那条路一个字节都没变（按 `seqvel-verify-loop`
    §3 的触发条件，本改动不在该跑之列）。

- **R3（把 R1 / R2 的前提补上：监听器拿到的是求值副本，写必须落在原始数据块上）**
  R1 与 R2 都默认了一件事——"监听器里那些写**真的写进去了**"。用户复诊（v1.6.3 之后）：
  "在有曲线的时候，把素材末端拉长，拉长的部分是黑屏，而没用根据速度来计算出来；
  但是如果动一下最后的那个速度点的话，触发了一下更新，画面就好了。"
  真机日志显示**链子完整跑过**（`observe_strip → True` → `relay_span` →
  `invalidate_speed_map` 返回空串、`diag.invalidated = True`），画面照旧黑
  —— **"函数被调用过"这条判据在这里彻底失效**。
  - **根因**：`depsgraph.updates[i].id` 是**求值副本（copy-on-write）**，不是原始
    数据块。经副本做的每一处 RNA 写都被**静默丢弃**：`speed_control` 只是副本的
    **结构体字段**（其 RNA 更新回调 `rna_Strip_invalidate_raw_update` 用
    `ptr->owner_id`，于是 `relations_invalidate_cache_raw` 作用在**副本场景**上）；
    `clear_keys` / `insert_keys` 动的是副本的 fcurve；自定义属性（模型载荷）在副本上
    是另一份。**而 `diag` 照样报 `invalidated: True`** —— 面板与既有 555 条用例
    一致地说"成功"。**回调入参 `scene` 才是原始**（实测 `is_evaluated=False`）。
  - **真机判据**（`.scratch/extend-blackout/evidence.md`）：
    - 真窗口日志（`probe_02_gui_log.py`，429 条）：用户拖源条带右端时区间

## 后人不该"简化"回去的理由

"模型不随条带变化"曾是写明的语义（`set_duration` 注释）。跟随上线后该语义
只对**模型**成立——"点集与速度值不改"，**不代表承载层可以不动**。若有人把
监听器里那条重落地当成"多余的对齐"删掉，或把 `right >= last` 那类短路写回来，
"拉长出来的那一段不响应 / 播放不正常"会复发，而且**无报错**——它就是本次
修订 R1 的病灶。**同理，也不要把 `write_curve` 收尾那次重建当成"重复劳动"删掉**
（修订 R2）：那张表不认"我刚刚写过 key"，只认"有人显式让我重算"，漏掉它整条条带的
画面都会停在写入中途那一份上，而且**逐帧看起来都"有变化"、不报错**。回归测试须覆盖：越过末点跟随、连续吞点、2 点保底、旧数据
钳回、**拉长不带动模型但必须重落地（且不重写关键帧）**、**左裁 / 整体移动
必须重锚关键帧**、**首次见到只重建映射表、不写属性**、
**全量写入收尾必须重建映射表（且失败要把原因递到面板）**、**监听器的目标必须是原始数据块（写副本会被静默丢弃）**。
