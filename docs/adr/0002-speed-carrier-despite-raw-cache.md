# 明知 Raw 缓存会吞子帧，仍坚持 Speed Control 承载

## Status

accepted —— 关掉混合帧（ADR-0001）之后，用户报告"掉帧、不是无级变速"，本轮把
根因定位到上游缺陷并决定**不因此迁移承载机制**，插件侧只提供用户点击的补救入口。

## 背景

ADR-0001 关掉 `use_frame_interpolate` 后，场景条带的小数源位置原样传给
`seq_render_scene_strip_ex` 的 subframe —— 理论上真·无级。但用户实测"重影是没了，
但是会掉帧"。

根因（证据见 `research/source-image-cache-subframe.md`）：VSE 源图缓存的
get / put **先 `math::round(timeline_frame)` 再建键**
（`cache/source_image_cache.cc` L143 / L193，写入受 `use_cache_raw` 控制，
默认开）。Speed Control 把小数源位置放在 `timeline_frame` 里，于是同一个整数
源帧内的输出帧撞同一个键 —— 实测 0.25x 渲染 10 帧，源场景只被求值 3 次
（关缓存则逐帧命中期望）。原生 Retiming 的小数产生在 `give_frame_index`、
即取整**之后**，键每帧唯一，所以它怎么慢都流畅。

## 决定

1. **承载仍走 Speed Control**，不迁回原生 Retiming。
2. 面板在"承载绑定的输入是场景素材 + 本场景 `use_cache_raw` 开"时显示
   **无级受限**并给一键开关「关闭 Raw 缓存（恢复无级）」；关掉后按钮变为
   「打开 Raw 缓存」（可再点恢复）。
3. **不由插件自动关缓存**：缓存是场景级设置，自动改用户的项目设置、且会连带
   影响同场景无关条带的性能，与"不越权"的既定立场相冲。
4. 向上游提交缺陷报告（草稿：`research/upstream-report-source-image-cache.md`）。

## 考虑过的选项

- **迁回原生 Retiming 承载**：否。Retiming 的首末 key 把映射两端钉在源 0 与源
  `len` 上，慢放只能靠把条带在时间轴上拉长（顶开相邻条带、改变时间轴），与
  "长度不变、只消费一部分源"的语义不同；段速度与源位置 RNA 读不回；不支持负
  速度；表达不了"倾斜渐变"。这些在 `research/speed-carrier.md` §7a 已有结论，
  本缺陷没有改变其中任何一条。
- **落地时自动关缓存**（记下原值、删除速度线时恢复）：否。"开箱即无级"很诱人，
  但用户可能不希望自己的缓存设置被一个插件悄悄改掉；恢复时机也无法覆盖
  "删了速度线但还想要无级"的情况。改为面板提示 + 一键，代价是首次使用要多点一下。
- **只提示不给按钮**：否。那等于"开箱即坏"，把修复成本全部推给用户去翻文档。

## 后人不该改回去的理由

- "Retiming 更平滑"在这台机器上不成立：它流畅**正是因为**它的小数没被缓存取整；
  Speed Control 的小数被取整，不是 Speed Control 模型本身的问题。关掉 Raw 缓存
  后两者同为无级（实测第一组序列逐帧吻合）。
- 面板上的"无级受限"提示是这条决定的日常出口：用户看到掉帧时第一眼就能知道
  这是上游缺陷、有一个按钮可解，而不是以为插件坏了。
- 上游修复后，`tools/probe_scene_strip_time.py` 会以 MISMATCH 退出 —— 那时
  面板提示可以撤掉，但承载机制的选择不受影响。
